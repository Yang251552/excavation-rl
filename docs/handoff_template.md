# Session Handoff — Template & Rules

This file defines how to write a session handoff in this project. Read it once when the user asks to write or read a handoff. Everything here is convention; deviating without a stated reason makes future sessions harder to pick up.

---

## When to write a handoff

Write one **only** when the user explicitly triggers it. Examples of valid triggers:

- "Write a handoff."
- "Save state, we'll continue tomorrow."
- "Let me come back to this."

Do **not** write a handoff for:

- General Q&A about the project (clarification, conceptual questions, "what does X mean").
- Read-only exploration / status checks.
- Routine "the experiment finished, here are the numbers" — those go in `docs/<stage>_tuning_log.md` per CLAUDE.md §4.5.
- Sessions where the project state at end is the same as at start (no edits, no decisions, nothing queued).
- General-inquiry windows the user has flagged as not project work.

If unsure, ask the user once: *"This session has [...] queued — write a handoff?"* Don't auto-write.

---

## Storage convention

```
Path:   docs/session_handoffs/<YYYY-MM-DD>_<topic-slug>.md
Sort:   Filename = chronological (lexical sort = date sort)
Group:  Single flat folder; no subfolders unless ≥200 files
Delete: Never. After 6+ months, may move to docs/session_handoffs/archive/
```

### Topic-slug is auto-generated by you (the LLM)

**Do not ask the user for a topic.** Derive it from the session's primary subject and pick a short, specific, lowercase-with-underscores identifier. Aim for 2–5 underscored words, ≤ 40 chars.

Examples (good):
- `stage1_5_v28_analysis` — session analysed v28a/v28b wandb results
- `readme_refactor` — session slimmed README + added appendices
- `v29_anchor_design` — session designed a new KL anchor variant
- `handoff_protocol_setup` — session set up handoff template + storage convention
- `bug_fix_obs_normalization` — session diagnosed and fixed obs-rms freeze pathology

Examples (avoid):
- `update` / `changes` / `notes` — too generic
- `worked_on_stage1_5_things_today` — verbose
- `2026-05-03-session` — date is already in the filename, redundant

**If the session covered multiple things**, pick the one most load-bearing for future pickup (the topic future-you will most want to find). If there is genuinely no single primary subject, use `mixed_<two-or-three-words>` (e.g. `mixed_readme_and_v29_planning`).

**Same-day collision**: prefer a more specific topic-slug rather than date suffixes. Only add `_a` / `_b` when two handoffs on the same day genuinely cover overlapping topics.

No `INDEX.md`, no per-stage subfolders. Filename sort + `ls` is enough up to ~200 files.

## Required sections (numbered; omit if empty but keep numbering)

1. **What this session completed (facts)** — bullet list, no narrative. Each bullet is one verifiable change with a file path or wandb run-id.
2. **Queued next actions (priority order)** — what the next session should do first. Numbered, each with a one-line *why*.
3. **Decisions that should not be re-litigated** — disproved hypotheses, gates set, choices the user endorsed. Cite the evidence (metric value, quoted decision).
4. **Quantitative summary** — final-window metrics + run-id mappings. Pull via wandb API per CLAUDE.md §2; never paste truncated stdout.
5. **Candidate next directions (if open)** — queued but not started.
6. **Currently running / waiting** — open background runs, pending `ScheduleWakeup`, anything the new session might trip over.
7. **References** — pointers to the most relevant files for cold pickup. Saves the new session a `find . -name "*.md"`.
8. **Unresolved threads** — observations not in §2 priority but worth flagging.

Numbering matters: future sessions navigate handoffs by section number ("read §3 to know what's been ruled out"). Don't drop or renumber sections.

---

## Hygiene

- **Prior handoffs are immutable.** Never edit an old handoff; supersede with a new file. Like tuning-log entries (CLAUDE.md §4.5), they are point-in-time snapshots.
- **Done items don't carry over.** When the current session completes a queued action from a prior handoff, mention it in this handoff's §1 ("Done: V26-V28 tuning log entries from `2026-05-03` handoff"). Do NOT re-queue it in §2 unless deliberately reprioritised.
- **Span topics freely.** One handoff covers whatever the session worked on (regardless of which stage / area). Don't write per-stage handoffs from a single session.

---

## Anti-patterns

- Writing the handoff at session start or middle — write at the end in one pass with full context, not as a draft you keep editing.
- Free-form prose without numbered sections — the numbered structure is what makes handoffs cheap to skim.
- Pasting tool-call transcripts — compress to decisions and outcomes only.
- Triggering on "wandb run finished" — that's a tuning-log event, not a session-boundary event.
- Auto-writing without explicit user trigger — handoffs are user-requested, not automatic outputs.
- Including every fact you learned this session — handoffs are queued state for next session, not session logs.
